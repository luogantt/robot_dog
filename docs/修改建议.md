# ASDU UDP Control 修改建议 README

> 适用对象：S10 / CD1 机器人 ASDU UDP 控制脚本  
> 适用用途：团队内部代码评审、后续重构、向厂商技术支持确认接口行为  
> 结论：当前代码的 **ASDU 帧格式、主要 Type/Command、枚举值整体正确**。主要问题不在协议帧层，而在 **运动控制语义、状态机、周期发送、错误处理和安全退出**。

---

## 1. 先明确：哪些部分暂时不需要大改

当前代码以下部分总体可以保留：

- ASDU 16 字节协议头结构
- 同步字 `EB 91 EB 90`
- 小端字节序
- JSON 格式标志 `0x01`
- 协议版本 `0x01`
- `msgId` / `packetId` 自增逻辑
- 心跳：
  - `Type = 0x00100064`
  - `Command = 0x00000005`
- 运动状态转换：
  - `Type = 0x00100001`
  - `Command = 0x00200002`
- 步态切换：
  - `Type = 0x00100001`
  - `Command = 0x00300002`
- 普通轴指令：
  - `Type = 0x00100001`
  - `Command = 0x00100002`
- 状态包中 `BasicStatus` / `MotionStatus` 的基本解析思路

因此，建议不要重写底层协议封装，而是重点重构 **RobotClient 上层控制逻辑**。

# 3. P0：必须修改 `send_velocity_burst()`

当前实现类似：

```python
body = make_velocity(...)
apdu, _ = build_apdu(body)

deadline = time.time() + duration

while time.time() < deadline:
    self.sock.sendto(apdu, target)
```

这里存在两个问题。

## 3.1 同一个 APDU 被重复发送

当前 `build_apdu()` 只调用一次。

因此整个 burst 期间：

- `msgId` 不变
- `packetId` 不变
- `Time` 不变
- UDP payload 完全相同

这与协议中“报文 ID 逐帧递增”的语义不一致。

### 修改建议

每次发送前重新构造报文：

```python
while time.monotonic() < deadline:
    body = make_velocity(x, y, z, roll, pitch, yaw)
    apdu, _ = build_apdu(body)
    self.sock.sendto(apdu, target)
```

---

## 3.2 当前发送频率完全失控

当前循环没有 `sleep()`，实际上不是控制周期，而是：

```text
CPU 能多快发，就多快发
```

这会形成大量无意义 UDP 包。

不建议这样做。

### 建议改为固定频率

例如：

```python
def send_velocity(
    self,
    x=0.0,
    y=0.0,
    z=0.0,
    roll=0.0,
    pitch=0.0,
    yaw=0.0,
    duration=1.0,
    hz=20,
):
    period = 1.0 / hz
    deadline = time.monotonic() + duration

    while time.monotonic() < deadline:
        body = make_velocity(x, y, z, roll, pitch, yaw)
        apdu, _ = build_apdu(body)
        self.sock.sendto(apdu, (self.host, self.port))
        time.sleep(period)
```

### 推荐

对于这种上层速度控制：

```text
10 Hz ～ 20 Hz
```

先足够用于测试。

如果后续接自主导航控制器，再根据厂商建议和实际响应频率决定。

# 4. P0：增加异常退出时的停止保护

当前流程：

```python
client.start()

...
client.send_velocity_burst(...)
...
client.stop()
```

如果程序中间发生：

- `Ctrl+C`
- Python 异常
- UDP 发送异常
- 状态机异常退出

则最后的速度归零代码不一定会执行。

对于机器人控制，这个风险不建议保留。

## 建议

整个主流程必须使用：

```python
try:
    run_commands()

finally:
    client.stop_motion()
    client.stop()
```

例如：

```python
def stop_motion(self):
    target = (self.host, self.port)

    for _ in range(10):
        body = make_velocity(0, 0, 0, 0, 0, 0)
        apdu, _ = build_apdu(body)
        self.sock.sendto(apdu, target)
        time.sleep(0.05)
```

注意：

不要像原代码一样瞬间连续发送 5 个零速包。

更建议：

```text
连续多个控制周期发送零速度
```

这样停止行为更符合控制系统语义。

# 5. P1：站立完成条件不要只等待 `MotionState == 1`

当前：

```python
client.send(make_motion_state(1), "起立")

wait_for_state(
    client,
    target_motion=1,
)
```

存在误判可能。

通过 ASDU 下发站立以后，机器人完成站立动作后，会自动进入：

```text
MotionState = 17
RL 控制状态
```

因此真实状态过程可能是：

```text
1
↓
起立
↓
17
```

如果状态包没有恰好被程序采到 `1`，程序可能会显示：

```text
站立超时
当前 MotionState=17
```

但机器人实际上已经完成起立。

## 建议

如果目的是：

> 判断机器人已经完成起立、可以继续接受运动控制

则应该等待：

```python
MotionState == 17
```

例如：

```python
if wait_for_state(client, target_motion=17, timeout=15):
    print("[OK] 已起立并进入 RL 控制")
```

或者将状态过程分开记录：

```text
收到 1：进入站立过程
收到 17：站立完成，可运动
```

---

# 6. P1：`MotionState == 17` 不等于“机器人已经完全停止”

这一点需要和上面的修改一起理解。

进入：

```text
MotionState = 17
```

只说明：

> 已进入 RL 控制状态。

它不表示：

```text
LinearX == 0
LinearY == 0
AngularZ == 0
```

而步态切换要求机器人完全停止。

所以不能把：

```python
time.sleep(2)
```

当成严格的“停止确认”。

## 建议增加：

```python
wait_until_stopped()
```

基于 MotionStatus：

```text
LinearX
LinearY
AngularZ
```

例如：

```python
def wait_until_stopped(
    client,
    linear_threshold=0.02,
    angular_threshold=0.03,
    stable_time=0.3,
    timeout=5.0,
):
    ...
```

判据可以先设为：

```text
abs(vx) < 0.02 m/s
abs(vy) < 0.02 m/s
abs(wz) < 0.03 rad/s
```

并持续：

```text
300 ms
```

再认为真正停止。

状态机应该是：

```text
STAND
  ↓
RL_READY
  ↓
STOPPED
  ↓
GAIT_SWITCH
```

而不是：

```text
STAND
  ↓
sleep(2)
  ↓
GAIT_SWITCH
```

# 8. P1：修改 `X=0.12 ≈ 0.2m/s` 的注释

当前代码：

```python
X=0.12  # ≈ 0.2m/s
```

这个写法不够严谨。

对于：

```text
Command = 0x00100002
```

`X=0.12` 的正式含义是：

```text
最大前进速度的 12%
```

不是直接的：

```text
0.12 m/s
```

虽然如果最大速度按约 `1.67 m/s` 推算：

```text
1.67 × 0.12 ≈ 0.20 m/s
```

但协议没有保证普通比例轴指令和真实轴指令一定按完全相同的最大速度映射。

## 建议改注释为

```python
# X=0.12：最大前进速度的 12%
# 若当前最大速度约为 1.67m/s，则约为 0.20m/s
```

如果改成真实轴指令，则可以直接写：

```python
X = 0.2  # m/s
```

# 9. P1：必须处理 ErrorCode / ErrorMessage

当前接收线程主要提取：

```text
MotionState
Gait
Mode
```

但协议请求还会返回通用调用状态，例如：

```json
{
    "Items": {
        "ErrorCode": 0,
        "ErrorMessage": "Success"
    }
}
```

失败时可能出现：

```text
0xE004 Missing necessary fields
0xE005 Mismatched data type
0xE006 Mismatched request client
0xE007 No operation permission
0xE008 Not allowed operation
0xE009 Operation failure
0xE00A Unsupported function
0xE00B Internal error
```

如果不打印这些错误，就可能发生：

```text
发送步态切换
↓
机器人明确返回错误
↓
程序忽略
↓
10 秒后
↓
只打印“等待步态超时”
```

这会严重降低排查效率。

## 建议

接收线程增加：

```python
items = body.get("PatrolDevice", {}).get("Items", {})

if "ErrorCode" in items:
    print(
        "[RESPONSE]",
        "ErrorCode=", items.get("ErrorCode"),
        "ErrorMessage=", items.get("ErrorMessage"),
    )
```

更进一步，应建立请求/响应匹配机制。

# 10. P1：利用 `msgId` 做真正的 request-response

协议中的 `msgId` 本来就用于：

```text
请求和响应匹配
```

目前代码虽然生成了 `msgId`，但没有真正利用它。

建议增加：

```python
pending = {}
```

发送时：

```text
msgId = 105
pending[105] = Event / Future
```

接收时：

```text
收到 msgId = 105
↓
解析 ErrorCode
↓
唤醒对应请求
```

以后接口可以写成：

```python
result = client.send_command(
    make_gait_switch(0x3003)
)

if not result.success:
    ...
```

这样比单纯：

```text
发命令
↓
等状态变化
```

更可靠。

最好把：

```text
命令是否被接受
```

和：

```text
机器人是否执行到目标状态
```

分成两个层次。

# 11. P2：`_last_status` 不应该整字典覆盖

当前逻辑类似：

```python
self._last_status = {
    'MotionState': ms,
    'Gait': gait,
    'Mode': mode
}
```

但是：

### BasicStatus

有：

```text
MotionState
Gait
ControlUsageMode
```

### MotionStatus

有：

```text
MotionState
Gait
LinearX
LinearY
...
```

但没有：

```text
ControlUsageMode
```

因此状态会出现：

```text
BasicStatus:
Mode = 0

↓ MotionStatus 到达

Mode = None
```

即有效状态被新包覆盖掉。

## 建议

改成增量更新：

```python
if ms is not None:
    self._last_status["MotionState"] = ms

if gait is not None:
    self._last_status["Gait"] = gait

if mode is not None:
    self._last_status["Mode"] = mode
```

并进一步把：

```text
LinearX
LinearY
AngularZ
```

也保存进去。

# 12. P2：共享状态建议加锁

当前：

```text
recv thread
```

会写：

```python
self._last_status
```

主线程同时读。

Python 下简单字典操作多数情况下不会直接崩溃，但从设计上最好不要依赖这种行为。

建议：

```python
self._status_lock = threading.Lock()
```

写：

```python
with self._status_lock:
    ...
```

读：

```python
@property
def last_status(self):
    with self._status_lock:
        return dict(self._last_status)
```

这样后面状态字段增加时也更安全。

---

# 13. P2：不要吞掉所有 Exception

目前类似：

```python
except Exception:
    pass
```

和：

```python
except Exception:
    continue
```

不适合正式调试。

因为：

```text
协议解析 bug
socket bug
JSON bug
逻辑 bug
```

最后都会被静默吃掉。

建议至少：

```python
except Exception as e:
    print(f"[ERROR] recv loop: {e}")
```

正式版本可以接 `logging`。

心跳线程也一样。

---

# 14. P2：时间控制使用 `time.monotonic()`

运动周期和 timeout 不建议使用：

```python
time.time()
```

因为系统时间可能被 NTP 调整。

建议：

```python
time.monotonic()
```

用于：

- timeout
- deadline
- velocity period
- stable stop 判断

`datetime.now()` 仍然可以继续用于协议报文中的 `Time` 字段。

# 15. P2：停止心跳前建议先确保机器人处于安全状态

现在执行顺序：

```text
趴下
↓
client.stop()
↓
停止 heartbeat
```

方向是对的。

建议把退出过程固定化：

```text
发送零速度
↓
确认停止
↓
趴下（按需要）
↓
等待趴下状态
↓
停止 heartbeat
↓
关闭 socket
```

异常退出场景至少保证：

```text
零速度
```

先于 socket close。

# 20. 最终判断

当前代码：

```text
ASDU 协议帧            基本正确
Type / Command         基本正确
心跳机制               基本正确
状态监听               基本可用
--------------------------------
控制周期               需要修改
状态机                 需要修改
请求响应机制           需要增强
异常处理               需要增强
安全停止               必须增强
自主导航接口选择       需要先确定
```

因此不建议推倒重写。

最合理的方向是：

> **保留协议封装，重构 RobotClient 和 MotionController。**

当前脚本很适合作为：

> **ASDU 接口连通性和基本动作测试程序**

但如果要进入正式的 S10 自主导航 / 自主爬梯链路，还需要把它升级成：

> **固定周期控制 + 状态机 + 真速度接口 + 错误响应 + 安全停车**

的底盘控制层。
