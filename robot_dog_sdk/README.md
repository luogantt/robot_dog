# 山猫 S10 机器狗控制 SDK

基于《软件开发指南》V1.0.1 的 ASDU/UDP 协议实现，包含**协议层、Web 遥控界面、命令行工具和模拟机器人**。

> 协议依据：文档 §1.1.5（16 字节协议头）、§1.2.x（控制类指令）、§1.3.x（状态上报）、§1.5（通用错误码）、§2.2.1（状态机）。
> 完整文档见 [docs/软件开发指南.pdf](docs/软件开发指南.pdf)，可搜索文本版见 [docs/guide_utf8.txt](docs/guide_utf8.txt)。

## 0. 先搞清楚谁是谁：本 SDK 是客户端，机器狗是服务端

文档 §1.1.2 原文：**"机器人本体为 TCP/UDP 服务端，外部板卡或系统为 TCP/UDP 客户端。"**

```
机器狗 10.21.33.103                     你的电脑
┌──────────────────────────┐            ┌───────────────────────────┐
│ robotserve               │            │ web_control.py            │
│  ← 厂商的服务，开机即在跑  │◀───────────│ asdu_udp_control.py       │
│    监听 UDP 30004         │    UDP     │ tools/asdu_cli.py         │
│                          │            │  ← 这些才是要启动的东西    │
└──────────────────────────┘            └───────────────────────────┘
```

| | 机器狗上 | 你的电脑上 |
|---|---|---|
| 要启动什么 | **什么都不用启动** | `web_control.py` 等客户端 |
| 要做的事 | 让技术支持**关掉 30004 的 DTLS 加密** | 运行本目录下的脚本 |

> 在机器狗上唯一要做的事就是关加密。文档说明这个配置文件**系统更新不会覆盖**，改一次即可。

## 1. 快速开始

### 1.0 用启动脚本（最简单）

**Windows**：双击 `start.bat`，弹出菜单选即可。

```
[1]  本机仿真      模拟机器狗 + Web 界面（不碰真机，先玩这个）
[2]  只读观察真机   只发心跳，不发任何运动指令
[3]  控制真机       可操控有风险的，请先确认环境安全
[4]  查询真机状态   命令行只读检查
[5]  环境自检
```

也可以在命令行直接指定模式（跳过菜单）：

```powershell
.\start.bat check      # 只检查环境
.\start.bat status     # 只读查询真机状态
.\start.bat sim        # 本机仿真
.\start.bat observe    # 只读观察真机
.\start.bat control    # 控制真机
```

> **PowerShell 下必须带 `.\` 前缀** —— PowerShell 出于安全考虑不会从当前目录执行命令，
> 直接打 `start.bat` 会报「无法将"start.bat"项识别为 cmdlet」。用 cmd.exe 或双击则不受影响。

**Linux**（机器狗主机）：用法相同，把 `start.bat` 换成 `./start.sh`。

脚本会自动找 Python、检查依赖、自动打开浏览器、检测端口占用。

> 为什么 `start.bat` 里一个中文都没有：cmd.exe 按当前代码页**逐字节**读 `.bat` 文件，
> UTF-8 中文会让字节错位、把后面的行解析错。所以批处理只保留 ASCII 外壳，
> 菜单和全部提示都在 `start.py` 里（跨平台共用一份）。

### 1.1 先在本机跑（不需要真机）

模拟机器人忠实实现了文档里的行为（起立自动进 RL 控制、步态切换需停止、状态上报频率、故障推送），
**不接真机就能把界面调熟**。

```bash
# 终端 1：启动模拟机器人
python robot_sim.py 31004

# 终端 2：启动 Web 服务，指向模拟器
python web_control.py --host 127.0.0.1 --port 31004
```

浏览器打开 **http://127.0.0.1:8000**

### 1.2 接真机

```bash
python web_control.py                    # 默认 10.21.33.103:30004
python web_control.py --host 192.168.1.50 --port 30004
```

**运行前必须确认**：`robotserve` 配置里 **30004 端口的 DTLS 加密已关闭**（文档 §1.1.2）。
默认是加密的，需要联系技术支持改配置文件。不关的话脚本收不到任何回包。

## 2. 三种用法

| 入口 | 用途 |
|---|---|
| `web_control.py` | **Web 遥控**：按住按钮/摇杆操控，实时状态，急停 |
| `tools/asdu_cli.py` | **命令行**：相当于这个协议的 `curl`，逐条发指令排查问题 |
| `tools/demo_send_command.py` | **教学**：看懂"一条命令怎么拼出来"，默认不发送 |
| `robot_sim.py` | **模拟机器人**：开发调试用 |
| `asdu_udp_control.py` | **协议层 + RobotClient**：被上面几个复用，也可直接跑完整流程 |

```bash
# 命令行工具示例
python tools/asdu_cli.py status            # 只发心跳看状态上报
python tools/asdu_cli.py stand             # 起立
python tools/asdu_cli.py gait 0x1003       # 切楼梯步态
python tools/asdu_cli.py axis 0.12         # 轴指令 X=0.12，2 秒后自动归零

# 对着模拟器用
set ASDU_HOST=127.0.0.1 & set ASDU_PORT=31004 & python tools/asdu_cli.py status

# 完整流程脚本（起立→切步态→前进→趴下）
python asdu_udp_control.py
```

## 3. Web 遥控界面

### 操控方式
- **按住持续动**：方向键 + 左移/右移（鼠标和触屏都可以）
- **虚拟摇杆**：上下=前后，左右=转向（手机/平板体验最好）
- **键盘**：`W/S` 前后、`A/D` 转向、`Q/E` 平移、`空格` 急停

### 面板
步态切换（4 个）、机身动作（起立/趴下）、使用模式切换、速度上限滑条、急停、实时状态、事件日志。

### 四层安全闸

| 闸 | 行为 |
|---|---|
| 看门狗 | 400ms 内没收到浏览器意图 → 目标速度归零 |
| 状态门 | 收不到状态上报 / HES 触发 / 故障 ≥ERROR / 非 RL 控制(17) → 拒绝运动 |
| 限幅 | 速度上限 + 每周期变化量限幅（避免瞬间满速） |
| 时长限制 | 连续运动超过 30s 强制归零，需松开重新按 |

关标签页、浏览器崩溃、笔记本休眠这三种情况都由**看门狗**统一兜住 ——
因为服务端持续以 20Hz 下发指令，任何故障都只表现为"指令停发"。

## 4. ⚠️ 三条必读注意事项

### 4.1 本软件的"急停"是软件零速，不是硬件急停

文档 §1.2.3 明确：**软急停(-2)仅支持查询，不支持通过 ASDU 下发**。这份文档里**没有急停指令**。
所以界面上的"急停"按钮只是**持续下发零速度**。

> **真正的安全手段是机器人本体的物理急停按钮。** 软件急停不能替代人在现场看护。

### 4.2 使用网页遥控时，请关闭手机 App 的手动控制

文档 §1.5 的 `0xE006`：**"轴指令发送时，要求 2s 内发送的指令来自同一个客户端"**。
手机 App 和网页在同一个 2s 窗口内发轴指令会互相踢掉，表现为"指令偶尔没反应"，极难排查。

### 4.3 文档里没有"上高台/越障"步态

全文只有 4 个步态值，地形只有**平地和楼梯**：

| 值 | 含义 |
|---|---|
| `0x1001` | 基础（常规运动模式） |
| `0x1003` | 楼梯（常规运动模式） |
| `0x3002` | 平地（导航运动模式） |
| `0x3003` | 楼梯（导航运动模式） |

如果厂商提供了新的步态值，在 `web_control.py` 的 `GAIT_CHOICES` 里加一行就会多出一个按钮。

## 7. 上真机的建议顺序

**第一次务必有人扶绳/看护，场地清空 2m 半径。**

1. 只连不控 —— 确认能收到状态上报，且界面显示的 `MotionState`/`Gait`/`Mode` 与手机 App 一致
2. 起立 —— 确认最终进入 `MotionState=17`（RL 控制）
3. **速度上限调到 0.05**，按住前进 0.5s —— **确认方向正确**（Yaw/X 符号可能相反）
4. 测松手后的滑行距离，据此调整 `WATCHDOG_MS`
5. 遥控中直接**关掉标签页**，测滑行距离
6. 直线走 10m，确认不跑偏
7. 逐步把速度上限提到 0.2~0.3，重测第 4、5 项
8. 切楼梯步态 → 确认使用模式自动变成导航 → 确认这时能正常运动（会自动改用真实轴指令）
9. 楼梯实爬：**在楼梯前切步态**，严禁进入楼梯后再切（文档 §1.2.4）

## 9. 实机验证记录

在真机（CD1 / Version=PRO）上实测到的、与文档不一致的地方。**改动代码前先看这里。**

### ✅ 2026-09-19：转向符号与文档相反

| | |
|---|---|
| 文档 §1.2.5 说 | "参数值的正负方向请**参考右手坐标系**确定"（该图在 PDF 文本版里丢失） |
| 实机表现 | 下发 `Yaw = +1`，机器狗实际**左转** |
| 结果 | 界面按"右转"会向左转 |
| 处理 | `web_control.py` 里加 `YAW_SIGN = -1.0` 统一取反，界面语义恢复正确 |

> 若厂商固件更新后此行为改变，把 `YAW_SIGN` 改回 `+1.0`，或启动时传 `--yaw-sign 1`。

### ✅ 2026-09-19：设备状态 / 导航状态上报的 Type 与文档不符

| 消息 | 文档写的 | 实机实际的 |
|---|---|---|
| 设备状态上报（电池/CPU/温度/GPS） | `0x0010 0002`（§1.3.1.3） | **`0x0030 0002`** |
| 位置/导航状态 | `0x0010 0003`（§1.4.2） | **`0x0030 0003`** |

文档里 `0x0030` 作为 **Type** 前缀一次都没出现过（只作为 Command 出现过）。
而且文档把设备状态写成 `0x0010 0002`，**和 §1.2.2「使用模式切换」的 Type 撞车了** ——
实机用 `0x0030 0002` 正好避开了冲突。**判断：实机是对的，文档表格印错了。**

> 不影响本 SDK 使用：`BasicStatus`(0x00100064) 和 `MotionStatus`(0x00100001) 的 Type 与文档一致，
> 状态解析走这两条。设备状态/GPS 我们本来就不解析。**建议反馈给厂商。**

### ✅ 已确认与文档一致的部分

| 项目 | 实测 | 文档 |
|---|---|---|
| BasicStatus 频率 | 2.0 Hz | 2Hz ✓ |
| MotionStatus 频率 | 9.9~10.0 Hz | 10Hz ✓ |
| 起立后自动进 RL 控制 | `1` → `17` | §2.2.1 ✓ |
| 趴下 | → `4` | §1.2.3 ✓ |
| 静止时的 `AngularZ` | `-0.0079 rad/s` 零点漂移 | 文档未提，远低于停止判定阈值 0.03 |

### ✅ 2026-09-20：站立/趴下能、轴指令不能 —— **根因：本机有两张网卡都能到 10.21.33.0/24**

**现象**：Web 界面上起立/趴下/步态切换都正常，**前进/后退/转向完全没反应**。

**根因**：开发机上**插了一张多余的网卡**，导致路由表里出现**两条 metric 都是 1 的等价路由**：

```
DestinationPrefix NextHop      InterfaceAlias  Metric
10.21.33.0/24     10.21.41.1   WLAN 3          1     ← 源 IP 10.21.41.18
10.21.33.0/24     10.21.41.1   WLAN            1     ← 源 IP 10.18.3.160
```

Windows 在这种情况下**会给不同 socket 选到不同网卡、用不同源 IP**。而机器人
**按源 IP:端口 认客户端**（文档 §1.2.1「向持续发送心跳的 IP 和端口上报」、
§1.5 的 `0xE006`）—— 于是 `web_control` 和 `axis_test` 变成了两个互相抢占的
客户端，谁都不是稳定的那一个。

**修复要两步，缺一不可**：

| # | 动作 | 为什么 |
|---|---|---|
| **1** | **拔掉多余的网卡** | 消除两条等价路由，源端点唯一 |
| **2** | **重启 `web_control`** | ❗ **socket 的路径状态是启动时确定的** —— 只拔网卡不重启，进程还在用旧路由，症状不变 |

> 只做第 1 步会以为"修了没用"。**实测踩过这个坑。**

**两步都做完后立即正常**（网页路径前进跑到 `LinearX = 0.87 m/s`，
与 `axis_test` 直连的 0.87 完全一致）。

> ⚠️ **教训**：只要机器上有多条通往 `10.21.33.0/24` 的路由，本项目的所有
> "发指令"行为都会变得不可预测。**排查任何"指令没反应"之前，先看路由表**：
> ```powershell
> Get-NetRoute -DestinationPrefix 10.21.33.0/24 | Select-Object InterfaceAlias,RouteMetric
> ```
> 正常应该只有**一条**。

**下面的排查记录保留** —— 它证明了"协议层/应用层全部无罪"，把问题精确地
逼到了**网络层的源端点**这一层，最后才由路由表解释通：

| 嫌疑 | 怎么排除的 | 实测 |
|---|---|---|
| ~~没拿到控制权~~ | WS `claim` 后读状态 | `can_control=True` |
| ~~状态门拦截~~ | 读 `gate` | `''`（空 = 不拦） |
| ~~只读观察模式~~ | 读 `observe` | `False` |
| ~~看门狗超时~~ | 按前端节奏 10Hz 持续发意图 | 意图一直新鲜 |
| ~~发送失败被暂停~~ | 读 `control_hz`（只在发送成功后才累加） | 稳定 20.0 |
| ~~报文格式错~~ | 用真代码组包，与 `axis_test` 逐字节比 | **164 字节完全相同** |
| ~~目标地址错~~ | 读进程命令行 + 探测日志 | `10.21.33.103:30004` ✓ |
| ~~机器人状态不对~~ | 读 BasicStatus | `MotionState=17` / 常规模式 / 无阻断故障 |
| ~~机器人轴通道坏~~ | 同期用 `axis_test.py` 直发同样指令 | `X=0.5` → `LinearX=0.88 m/s` ✅ |
| ~~指令值落在死区~~ | 发满量程 `out.x=-1.0` | 仍然没反应 |
| ~~包没发出去~~ | 本机 UDP 监听（dest 覆盖为 127.0.0.1） | **收到 34 个包**（24 帧 `X=-0.5` + 10 帧归零） |
| ~~控制循环那条链~~ | 同进程同 socket 直发，绕过 ControlLoop | 仍然不动 |
| **✅ 源端点** | 路由表 | **两条等价路由 → 两个源 IP** |

**留下两个可复用的调试接口**（`web_control.py`）：

```python
# 通过 WebSocket 直接让 RobotClient 的 socket 发轴指令，绕过 Teleop/状态门/限幅，
# 并可改发到任意地址（用来验证"包到底出没出这个进程"）
{"t":"probe","x":-0.5,"yaw":0,"seconds":2.0}
{"t":"probe","x":-0.5,"seconds":1.2,"dest":["127.0.0.1",39999]}
```

> **注**：这两台目标机（`.102` / `.103`）都**挡非白名单端口的入站 UDP**，
> 所以"往目标机发探测包"这条路是不通的（对照组验证过）。跨机抓包需在目标机
> 本机做，或在源机用 Wireshark/pktmon（需管理员权限）。

### （历史记录）以下是根因定位前的原始记录

**症状**：Web 界面上

| 操作 | 结果 |
|---|---|
| 起立 / 趴下 / 步态切换 | ✅ **正常** |
| 前进 / 后退 / 左转 / 右转 | ❌ **完全没反应** |

**已排除的原因**（每条都实测过，不是推测）：

| 嫌疑 | 怎么排除的 | 实测值 |
|---|---|---|
| 没拿到控制权 | WS 里 `claim` 后读状态 | `can_control=True` |
| 状态门拦截 | 读 `gate` 字段 | `''`（空 = 不拦） |
| 只读观察模式 | 读 `observe` 字段 | `False` |
| 看门狗超时 | 按前端节奏 10Hz 持续发意图 | 意图一直新鲜 |
| **发送失败被暂停** | 读 `control_hz`（只在发送成功后才累加） | **稳定 20.0** |
| **报文格式错** | 用真代码组包，和 `axis_test.py` 逐字节比 | **164 字节完全相同** |
| 目标地址错 | 读进程命令行 | 默认 `10.21.33.103:30004` ✓ |
| 机器人状态不对 | 读 BasicStatus | `MotionState=17` / 常规模式 / 无阻断故障 |
| **机器人轴通道坏** | 同期用 `axis_test.py` 直发同样指令 | **`X=0.5` → `LinearX=0.88 m/s` ✅ 能动** |
| 指令值落在死区 | 发满量程 `out.x=-1.0` | 仍然没反应 |

**最关键的一组对照**：

```
web_control 路径：out.x = -1.0 持续 3.25 秒  →  LinearX 恒为 0.003（静止噪声）
axis_test 路径：  X    = -0.5 持续 2.0 秒  →  LinearX 峰值 0.88 m/s（强烈响应）
```

**同一个机器人、同一个协议、同一台电脑、同样（逐字节相同）的报文 —— 一个动、一个不动。**

**剩余嫌疑（按可能性排序）**：

1. **`0xE006` 客户端冲突** —— 文档说要求"2s 内指令来自同一客户端"。
   官方 SDK 源码（`gamepad_interface.hpp`）里比较的是 **IP 而非 IP:端口**
   （`if (LastPerIp == "" || LastPerIp == cmd_info.ip)`）。
   ⚠️ **但若实机固件按 IP:端口 比较**，那么 `web_control` 的 socket 源端口
   和 `axis_test` 的源端口不同，两者会互相踢掉 —— 而 `axis_test` 每次运行
   **都新建一个 socket**，端口每次都变。
   **→ 下次验证：让两个客户端用同一个源端口，或把 web_control 的 socket
   显式 bind 到固定端口再试。**
2. **`web_control` 的 socket 未显式 `bind()`**（`asdu_udp_control.py:270`）。
   Windows 上未绑定的 UDP socket 在首次 `sendto` 时由内核分配端口 ——
   行为上应该等价，但没有实测验证过"端口在会话内是否稳定"。
3. 实机固件对"持续 20Hz 流"和"单次请求"的处理不同（**可能性低**，
   因为 `axis_test` 也是 20Hz 持续流）。

**为什么站立/趴下不受影响**：它们走 `ActionWorker → client.send_and_wait()`，
**完全绕开了 20Hz 控制循环和状态门**（见 `web_control.py` 的 `do_stand/do_crouch`）。
所以"动作能、轴指令不能"这个不对称，本身就把问题范围缩小到了
**控制循环这条路径**。
