## 0. 脚本意图

对照文档还原出的行为：

```
趴下 → 起立(MotionParam=1) → 切换楼梯步态(GaitParam=0x1003) → 发 2s 轴指令(X=0.12) → 趴下(MotionParam=4)
```

通信方式：明文 UDP `10.21.33.103:30004`，ASDU 载荷用 JSON，后台 1Hz 心跳 + 状态监听线程。

## 2. 问题清单

### P0 — 安全 / 会导致机器人失控

#### P0-1　速度 burst 无异常兜底，异常时机器人停在危险状态

**位置**：[asdu_udp_control.py:224-240](asdu_udp_control.py#L224-L240)

```python
deadline = time.time() + duration
count = 0
while time.time() < deadline:
    self.sock.sendto(apdu, target)   # ← 裸调用，无 try/except
    count += 1
```

**问题**：Windows 上 UDP 发送缓冲区耗尽会抛 `WSAENOBUFS(10055)`；此外还有网络不可达等异常。一旦抛出，异常会穿过 `send_velocity_burst` → `run_sequence` 直接终止进程。此时机器人停留在**楼梯步态 + 非零速度**状态，退出前既不归零也不趴下。整个 `run_sequence` 也没有 `try/finally` 兜底。

**影响**：脚本崩溃 = 机器人无人接管且带着速度指令。

**建议**：`send_velocity_burst` 内 `sendto` 包 try/except 并统计失败；`run_sequence` 全程 `try/finally`，finally 中发送速度归零 + `MotionParam=4` 趴下，且 finally 内的发送本身也要包 try/except。

---

#### P0-2　burst 循环无速率限制，全速灌包

**位置**：[asdu_udp_control.py:230-233](asdu_udp_control.py#L230-L233)

**问题**：`while time.time() < deadline:` 是 busy-loop，以 CPU 能跑的最快速度发 UDP，实测可达每秒上万包。文档 §1.2.8 对运动 SDK 模式的频率要求是"取值范围：[1, 200] 且能整除 1000"，全速灌包既不符合设计语义，也容易打满接收端 UDP 缓冲区导致丢帧。

**建议**：改为固定频率定时发送（建议 50–100Hz，与 SDK `Frequency` 语义对齐），用 `time.perf_counter()` 做绝对时间调度，避免累积漂移。

---

#### P0-3　从不校验机器人使用模式就下发轴指令

**位置**：[asdu_udp_control.py:274](asdu_udp_control.py#L274) 读取了 `ControlUsageMode`，但第 3 步发轴指令前从未校验。

**文档依据**：
- §1.2.2【注意】"常规模式下支持执行轴指令（见"1.2.5 运动控制"部分），导航模式下支持执行导航任务。"
- §1.2.5【注意】"该指令仅支持在常规模式和辅助模式下执行。"

**问题**：若机器人处于导航模式（`ControlUsageMode == 1`），轴指令会被拒（对应 `0xE008 Not allowed operation`），脚本却毫不知情地继续往下走。

**建议**：第 3 步前断言 `Mode == 0`；若非常规模式，先发 §1.2.2 使用模式切换（Type `0x00100002` / Cmd `0x00500002`，`{"Mode": 0}`）再继续。

---

#### P0-4　未处理 `0xE006` 同客户端 2s 窗口，且轴指令无响应导致错误不可见

**文档依据**（§1.5 通用错误码表）：
> `0xE006 Mismatched request client` —— "例如：**轴指令发送时，要求 2s 内发送的指令来自同一个客户端**"

**问题**：
- 代码用单个 socket 发送，源端口一致 ✅（这一点是对的），但**完全没有解析错误响应**。
- 更关键：§1.2.5 明确"**该指令不返回任何响应帧**"，也就是说轴指令被拒时你**根本看不到**，只能从机器人不动来推断。

**建议**：至少解析并打印通用错误码响应（`ErrorCode` / `ErrorMessage`），对 `0xE006/0xE007/0xE008` 做显式告警。注意如果同时开着官方 App 操作同一台机器人，会因客户端不一致持续触发 `0xE006`。

### P1 — 逻辑正确性

#### P1-1　第 1 步等待的目标状态不对（等 `1`，实际稳态是 `17`）

**位置**：[asdu_udp_control.py:280-285](asdu_udp_control.py#L280-L285)

```python
client.send(make_motion_state(1), "起立")
if wait_for_state(client, target_motion=1, timeout=15):
```

**文档依据**（§2.2.1 状态转换）：
> 【注意】通过 ASDU 接口下发站立指令后，机器狗在**完成站立动作后会自动进入 RL 控制状态**，此时用户可直接下发速度指令或切换步态指令。

状态流转为：`趴下(4) → 正在起立(1) → 自动进入 RL控制(17)`。

**问题**：`1` 只是"正在起立"的中间态，稳态是 `17`。
- 走运时会采到中间态 `1`，打印 `[OK] 已站立`（结果碰巧对）；
- 走运没采到（2Hz 上报，中间态窗口短）就报 `[!!] 超时`，但机器人其实**一切正常**，属于假告警。

**真正的问题**：**速度指令能否下发，取决于是否已进入 `MotionState == 17`（RL 控制）**，而脚本从未确认这一点就往下走了。

**建议**：等待目标改为 `17`，或接受集合 `{1, 17}` 并在继续前显式确认已到 `17`。

---

#### P1-2　步态切换前未确认"机器人完全停止"

**位置**：[asdu_udp_control.py:286-296](asdu_udp_control.py#L286-L296)

**文档依据**（§1.2.4）：
> 【注意】步态切换指令需在机器人完全停止后下发。若机器人仍有运动速度时下发指令，**该指令将被缓存，待机器人停止后才会执行，不会立即响应**。

**问题**：第 2 步前只 `time.sleep(2)`，没有确认速度已归零。目前仅靠"第 1 步 `wait_for_state` 超时白等 15s"才侥幸满足这个前提——一旦 P1-1 修好、等待提前返回，这个前提就**不再成立**，步态切换会被缓存而不生效。

**建议**：第 2 步前显式发速度归零并等待确认速度已停，再发步态切换。

---

#### P1-3　楼梯场景的选型与文档推荐路径相反（需业务确认）

**文档依据**（§1.2.4）：
> 【注意】在进行二次开发以实现自主导航功能时，**必须采用导航运动模式下的专用步态，并配合真实轴指令进行控制**。其中，平地导航应调用步态指令 `0x3002`；楼梯导航则须在**进入楼梯前**切换至步态指令 `0x3003`，**严禁进入楼梯后再进行切换**。

（§1.2.6 补充：真实轴指令 Type `0x00100001` / Cmd `0x00110002`，"仅在导航模式下生效"。）

**问题**：代码走的是 `0x1003`（楼梯-常规运动模式）+ `0x00100002`（轴指令）的**手动遥控路径**。

- 如果本脚本定位是**手动试机**：当前选型合理，无需改动，但应在注释中写明这一前提。
- 如果定位是**自主爬梯**：选型必须改为 `0x3003` + 真实轴指令 `0x00110002`，且**切换时机必须在进入楼梯之前**。

**两种路径不可混用**，这是本次审查中最需要业务确认的一点。

---

#### P1-4　burst 内 `msgId` / 包编号不递增，违反"每帧报文唯一标识"

**位置**：[asdu_udp_control.py:226-233](asdu_udp_control.py#L226-L233)

```python
body = make_velocity(x, y, z, roll, pitch, yaw)
apdu, _ = build_apdu(body)          # ← 只构建一次
...
while time.time() < deadline:
    self.sock.sendto(apdu, target)  # ← 同一 msgId 重复发送上万次
```

**文档依据**（§1.1.5）：
> 报文 ID：**每帧报文的唯一标识**，用于识别请求帧和响应帧的对应关系……从 0 开始递增，达到 65535 后重新从 0 开始。

**问题**：整个 burst 复用同一 `msgId` 和同一包编号，且 `_msg_id` 全程只前进 1。

**影响**：轴指令无响应，所以当前**大概率无害**；但一旦换成有响应的指令（如步态切换、状态转换）就会出错，属于埋雷。

**建议**：每包重新 `build_apdu()`（内层循环里构建，或至少手动递增 ID）。

## 3. 部署前提（文档硬要求）

**位置**：§1.1.2 协议端口号

> DTLS 服务端（UDP + 加密）地址与端口为 `10.21.33.103:30004`，TLS 服务端（TCP + 加密）地址与端口为 `10.21.33.103:30003`。**默认情况下，端口通信启用加密**；用户可通过修改 `robotserve` 配置文件关闭加密（**需联系技术支持**），且系统更新不会覆盖该配置文件。

**问题**：代码注释与 docstring 假定"encryption disabled"，但这需要**先联系技术支持修改 `robotserve` 配置**。该前提不成立时脚本连不上机器人。

**建议**：在 README / 脚本头部注明这一前置条件。
